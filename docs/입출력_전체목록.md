## 1. 연결 방식 — 데이터가 어떤 길로 오가나

### 1-1. 화면 ↔ 서버 : HTTP + JSON

```
브라우저(Vue)  ──HTTPS 요청──▶  FastAPI 서버
               ◀──JSON 응답──
```

| 항목 | 내용 |
|---|---|
| 규약 | REST. `GET`(조회) · `POST`(생성·실행) · `PATCH`(일부 변경) |
| 본문 형식 | JSON. 음성 업로드 2곳만 `multipart/form-data`, 파일럿 내보내기 1곳만 CSV |
| 인증 | 로그인 시 받은 **JWT 토큰**(HS256)을 매 요청 `Authorization: Bearer …` 머리에 싣는다 |
| 화면 쪽 코드 | `frontend/src/api.ts` 한 곳(axios). 401 이면 로그인 화면으로 보낸다 |
| 서버 쪽 입구 | `backend/app/api/endpoints/*.py` 10개 파일 |
| 형식 검사 | **입력**: Pydantic 스키마가 전부 검사(틀리면 422). **출력**: `response_model` 이 걸린 36개만 검사 |

### 1-2. 서버 안 모듈 ↔ 모듈 : 파이썬 함수 호출

네트워크가 아니다. **같은 프로그램 안에서 함수를 부르고 값을 돌려받는다.**

```
endpoints/diagnosis.py ──호출──▶ services/diagnosis/pipeline.run_sys01(db, session)
                                    ├─▶ judgment.judge_fluency(a4값들, 학년군)  → FluencyJudgment
                                    ├─▶ judgment.judge_comprehension(응답들, 학년군) → ComprehensionJudgment
                                    ├─▶ prescription.weakness_training_plan(…) → WeaknessPlan
                                    └─▶ environment.judge_environment(…) → EnvironmentResult
```

주고받는 값은 세 종류다.

| 종류 | 예 | 형식이 적힌 곳 |
|---|---|---|
| **dataclass** (모듈이 정의한 결과 묶음) | `FluencyJudgment`, `RoundAggregate` | 각 모듈 파일 |
| **enum** (정해진 값 목록) | `Level3` = low/mid/high | `models/core.py` |
| **DB 행 객체** | `JudgmentResult`, `TextContent` | `models/core.py` |

**중요** — 파이썬은 함수에 적힌 타입을 **실행 중에 검사하지 않는다.** 적어 둔 것은
설명일 뿐이라, 틀린 값이 들어와도 그 자리에서 멈추지 않는다. 지금 이 층을 지키는
것은 **테스트**(현재 350여 개)뿐이다.

### 1-3. 모듈 ↔ 저장소 : SQL

```
모듈 ──SQLAlchemy(비동기)──▶ asyncpg ──▶ PostgreSQL
```

한 모듈이 쓴 값을 **다른 모듈이 나중에 읽는** 경로다. 판정 결과를 리포트가 읽는
것이 대표적이다. 시점이 다른 두 모듈이 DB 를 사이에 두고 만난다.

| 칸 종류 | 검사 |
|---|---|
| 일반 칸 (숫자·문자·날짜·enum) | **DB 가 막는다.** enum 에 없는 값은 저장 자체가 안 된다 |
| **JSONB 칸 25개** | **아무 JSON 이나 들어간다.** 키 이름·값 형식을 아무도 검사하지 않는다 |

### 1-4. 서버 ↔ 파일

| 파일 | 방향 | 누가 | 형식 |
|---|---|---|---|
| `backend/app/data/survey_questions.json` | 읽기 | `survey/definition.py` | JSON — 학생 23문항 · 보호자 11문항 정의 |
| `backend/scripts/generated/seed_all.json` | 읽기 → DB 적재 | `scripts/load_content.py` (사람이 실행) | JSON — 지문 48편 + 문항 |
| 파일럿 내보내기 | 쓰기 | `GET /api/admin/pilot/export.csv` | CSV (UTF-8) |

### 1-5. 서버 ↔ 외부 서비스

| 상대 | 방식 | 보내는 것 | 받는 것 | 쓰는 곳 |
|---|---|---|---|---|
| **Naver Clova STT** | HTTPS POST (`httpx`) | 음성 바이트 | `{text, confidence, words, duration}` | 음독(비활성) |
| **Anthropic API** | HTTPS (공식 SDK) | 고정 응원 문구 1문장 | 다듬은 1문장 | 리포트 (키가 있을 때만) |
| **Silero VAD** | 로컬 ONNX 모델 파일 (네트워크 없음) | 음성 바이트 | 발화 구간 목록 | `/api/audio/timing` 참고용 |

콘텐츠 **제작** 때도 Anthropic 을 쓴다(`scripts/generate_content.py`, 사람이 실행).
서비스 운영 중에는 돌지 않는다.

### 4-3. JSONB 칸 25개 — 형식을 아무도 검사하지 않는 칸

**여기가 가장 약한 자리다.** 쓰는 코드와 읽는 코드가 키 이름을 "같이 알고 있다"고
가정할 뿐, 어긋나도 오류가 나지 않는다. 아래는 **작성 당시 코드가 실제로 쓰던 형태**다.

> **2026-09-25 갱신** — 판정·처방·리포트 경로의 9칸(`weakness_profile_12` ·
> `disclaimer_flags` ×2 · `recommended_texts` · `weakness_training_plan` ·
> `environment_adjustment` · `report_content` · `template_ids_used` ·
> `environment_level`)은 형식을 정해 저장·읽기 양쪽에서 검사한다. 모양도 바뀌었다
> (예: 약점 프로필은 칸마다 정답 수·문항 수, 추천 지문은 id 목록).
> 현재 형식은 `docs/데이터_형식_명세.md` 를 본다.

| 테이블.칸 | 실제 형태 | 쓰는 곳 → 읽는 곳 |
|---|---|---|
| `judgment_results.weakness_profile_12` | `{"A5_narrative": 0.83, "A5_expository": null, …}` **6칸** | 판정 → 처방·리포트 |

## 5. 파일 형식

**`survey_questions.json`** (버전 `2026-08-01-provisional`)

```
{ version, source, note, scale_direction,
  student: [23문항]  — active 9 · conditional 2 · reserved 12
  parent:  [11문항]  — active 10 · reserved 1 }

문항 1개: { code:"B-1", block, status, text, response_type, storage_field,
           required, options:[{label, value}], min/max, max_select_count, show_if … }
```

`storage_field` 가 DB 칸 이름이다. **설문 문항 ↔ DB 칸의 연결이 이 파일에 있다.**

**`seed_all.json`** — 지문 48편

```
[{ title, content, grade_group, genre, difficulty_level, syllable_count,
   text_structure, topic_tags,
   questions:[{ question_text, choices, answer_index, evidence_text,
                explanation, target_area }] }]
```

적재 스크립트가 품질 게이트와 태그 정본을 검사한 뒤 DB 에 넣는다.

## 6. 정리하다 발견한 것

> **2026-09-26 갱신** — 6-1·6-2 는 해결했다. API 66개가 응답 형식을 달고, 화면 타입은
> 서버 형식에서 자동 생성된다(`frontend/src/api-types.ts`). 남은 6개는 사유가 있다.
> 현재 형식은 `docs/데이터_형식_명세.md`.

### 6-1. API 출력의 절반은 형식 검사가 없다

72개 중 **36개**가 dict 를 그대로 내보낸다. 관리자·파일럿·파기·검수·계정·음성 API
전부다. 키 이름을 바꿔도 서버에서는 아무 오류가 나지 않고, 화면이 빈칸을 그린다.

### 6-2. 화면에 응답 타입 정의가 0개다

`frontend/src` 에서 API 응답의 형식을 적은 곳이 없다. **서버 ↔ 화면 경계를 지키는
장치가 없다.** 예외는 `label_5` 문구 한 곳이며, 이것도 테스트로 대조한다.

### 6-3. 학년이 세 가지로 적히고, 서로 대조되지 않는다

| 어디 | 형식 | 누가 정하나 |
|---|---|---|
| `users.grade` | `elem4`~`elem6` · `mid1` | 관리자가 계정 발급 때 |
| `student_profiles.grade` | 정수 4~7 | 학생이 설문 B-1 에서 |
| `texts`·`books.grade_group` | `G4_G6` · `G7` | 설문 학년을 변환 |

**판정은 설문 학년만 쓴다.** 계정이 `elem5` 인 학생이 설문에서 `7` 을 고르면
중1 기준으로 판정되고, 이를 잡는 곳이 없다.

### 6-4. `fluency_results.automaticity_score` 한 칸이 두 가지 뜻이다

음독이면 A1(음절/분)이 들어가고, 묵독이면 비어 있으며 A4(음절/초)는 다른 칸
(`a4_syllable_per_sec`)에 들어간다. 그런데 **응답 형식에 `a4_syllable_per_sec` 가
없어** 묵독 제출 응답에는 A4 값이 실리지 않는다.

### 6-5. 기록이 코드와 어긋나 있던 것 — 이번에 고쳤다

| 무엇 | 틀린 내용 | 고친 곳 |
|---|---|---|
| 흐름 레지스트리 | 콘텐츠 검수 API 를 **없는 경로** `/api/review/text/{id}/approve` 로 적음. 실제는 `POST /api/admin/reviews` | `flow_registry.py` |
| 그 검사 테스트 | 경로 첫 단어만 봐서 통과시킴 | 실제 라우트와 정확히 대조하도록 바꿈. 틀린 경로에서 실패하는 것 확인 |
| 확정필요 문서 1-1 | 구현 면책 코드를 6종으로 적음. 실제 **7종** (`fluency_partial_implausible` 누락) | `모듈간_데이터_확정필요.md` |
| 확정필요 문서 2-1 | `weakness_profile_12` 를 "12칸 고정"으로 적음. 실제 **6칸** | 같음 |

### 6-6. 화면이 부르지 않는 API — 10개 (문서·점검용 제외)

| 경로 | 상태 |
|---|---|
| `/audio/oral` · `/audio/timing` · `/audio/health` · `/diagnosis/fluency/oral` | 음독 비활성이라 연결 안 됨 |
| `/auth/me` | **항상 501** 을 돌려준다 |
| `/auth/users/{id}/name` · `/parent/survey/{profile_id}` | 화면 없음 |
| `/diagnosis/result/{id}` · `POST /diagnosis/round` · `PATCH /session/{id}/complete` | 구 흐름의 잔재로 보인다. 신규 흐름은 `start`·`round/complete`·`finalize` 를 쓴다 |

### 6-7. 아무도 불러오지 않는 파일

`backend/app/schemas/auth.py` — 어디서도 import 되지 않는다. 안에서 존재하지 않는
`Grade` 를 불러오므로, 누가 import 하는 순간 서버가 뜨지 않는다. 실제 인증 스키마는
`schemas/user.py` 다.
