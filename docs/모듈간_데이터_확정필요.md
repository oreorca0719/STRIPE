## 0. 이 문서가 다루는 것

각 모듈이 **무엇을 받아 무엇을 내보내는지** 중, **형식이 아직 확정되지 않았거나
두 곳에서 다르게 정의된 것**만 모았다. 이미 확정되어 잘 도는 것은 적지 않는다.

**왜 지금 필요한가** — 2026-09-24 하루에 결함 12건이 나왔고 10건이 우리 구현
결함이었는데, **전부 모듈이 만나는 자리에서 났다.** 부품은 각자 옳고 부품 단위
테스트는 통과하는데 서비스가 틀리는 형태다.

| 결함 | 어느 경계 |
|---|---|
| A1 단위 6배 차이 | 음독 산출 ↔ 유창성 경계값 |
| 라벨표 한 단계 어긋남 | 서버 ↔ 화면 |
| 태그 매칭 0/48편 | 지문 `topic_tags` ↔ 설문 `interest_topics` |
| 메타인지 전원 과소평가 | 설문 미수집 ↔ 판정식 |
| 타임아웃 회차 전멸 | 품질 게이트 ↔ 정렬 모드 |

**기획 쪽에 이미 대응물이 있다.** 기획상세명세 v1.2 **§9 「모듈 간 전달 데이터
명세」** 다(STR-127 본문에서 참조됨). 우리는 §9 전문을 받은 적이 없어 대조하지
못했다. **새 체계를 만들면 네 번째 사본이 되므로, §9를 정본으로 놓고 우리 구현을
붙이는 것이 맞다.** 아래 항목은 그 대조를 위한 우리 쪽 실측 목록이다.

**표기**

|---|---|
| 🔴 | 두 곳에서 **다르게** 정의돼 있다. 지금 어긋나 있다 |
| 🟠 | 정의가 **없다**. 암묵적으로만 돈다 |
| 🟡 | 정의는 있는데 **기획 확정 대기** |

## 1. 🔴 지금 어긋나 있는 것 — 4건

### 1-1. 면책 코드 (`disclaimer_flags`)

**이것이 가장 급하다.** 리포트가 코드만 저장하고 문구는 `report_templates` 에서
찾아 붙이는 구조라, **코드가 다르면 문준석이 문안을 만들어 줘도 붙지 않는다.**

```
계약 (Package #4 S5-FN-04)
  basic · unstable · silent_only · early_stop · grade_boundary · fluency_unavailable

구현 (report.py:149, judgment.py:70, pipeline.py:122)
  basic · fluency_unavailable · fluency_implausible · text_repeated
        · reliability_low · reliability_unstable
```

| | |
|---|---|
| 계약에만 | `silent_only` · `early_stop` · `grade_boundary` |
| 구현에만 | `fluency_implausible` · `text_repeated` · `reliability_low` |
| 이름만 다름 | 계약 `unstable` ↔ 구현 `reliability_unstable` |

**확정 필요** — 코드 집합과 표기. 구현에만 있는 셋은 우리가 실제 상황에서
만든 것이라 없애기 아깝다(특히 `text_repeated` 는 중복 지문 노출 사실을 남긴다).
계약에 추가할지, 다른 코드로 흡수할지 판단이 필요하다.

### 1-2. 지문 주제 태그 ↔ 설문 관심 주제

오늘 정본화했으나(`5c88be1`) **기존 데이터가 남아 있다.**

```
정본   C-1 선지 15종 (소문자)   animal · science · history · sports · mystery
                              fantasy · humor · friendship · family · art_music
                              cooking · game · world · horror · society

지문   48편 중 15편이 정본 밖    NATURE 6 · ADVENTURE 3 · SPACE 3 · DAILY 3
```

**확정 필요** — 15편을 어느 코드로 옮길지. 글 내용을 읽고 판단할 일이라 우리가
정하지 않았다. 참고로 C-1 라벨이 셋을 이미 품는다(`fantasy`="판타지·모험",
`animal`="동물·자연", `science`="과학·실험"). `DAILY`(일상)는 대응이 없다.

**함께** — 장르별 배분(어떤 주제를 이야기글/설명글로 쓸지)도 잠정이다. C-1
선지에는 그 구분이 없다.

### 1-3. 학생 노출 라벨 (`label_5` → 화면 문구)

오늘 맞췄고(`139d20b`) **가드도 걸었다.** 다만 구조적으로 두 곳에 남는다 —
서버 `report.py:STUDENT_LABEL`, 화면 `diagnosis.ts:LABEL_5`. 언어가 달라 공용
모듈로 묶을 수 없다.

**확정 필요** — 없음. 정본은 STR-123 이고 테스트가 대조한다. **기록용으로만 남긴다.**

### 1-4. 음독 `score_status` 에 B안 자리가 없다

```
계약   scored | unscorable
현실   전사 없이 감독자가 오류 수만 센 회차 → unscorable 로 떨어짐
```

계약은 STT 전사를 전제하는데, 파일럿에 감독자가 있으면 사람이 채점한 회차가
생긴다. **"채점됐으나 사람이 했다"를 담을 값이 없다.**

**확정 필요** — 값을 하나 더 열지, `unscorable` + 사유로 둘지. STR-132 질문 4번.

## 2. 🟠 정의가 없는 것 — 6건

전부 **JSONB 컬럼**이다. DB 를 지나는 순간 형식이 사라지고, 읽는 쪽이 키를
안다고 가정한다. 지금은 우리 코드끼리만 주고받아 돌지만, **문준석이 리포트
문안을 만들거나 부모·교사 리포트를 붙일 때 이 키들을 알아야 한다.**

### 2-1. `judgment_results.weakness_profile_12`

```json
{ "A5_narrative": 0.83, "A5_expository": null, "A6_narrative": 0.5, ... }
```

키는 `{영역}_{장르}` 이고 값은 정답률 또는 `null`(문항 0건 = 측정 안 됨).
**12칸 고정이며 `null` 과 `0.0` 은 다른 뜻이다.**

**확정 필요** — 키 표기(`A5_narrative` 형식), `null` 의미.

### 2-2. `prescription_results.recommended_texts`

```json
[{ "text_id": 1, "text_code": "TXT_...", "title": "...",
   "difficulty": "normal", "genre": "narrative", "topic_tags": ["animal"] }]
```

**확정 필요** — 항목 스키마. **특히 도서 추천(STR-108)이 붙으면 같은 키를 쓸지
다른 배열로 나눌지.** 지금 여기 들어가는 건 책이 아니라 진단 지문이다.

### 2-3. `prescription_results.weakness_training_plan`

```json
{ "needed": true, "cells": [ ... ] }      // needed=false 면 {"needed":false,"message":...}
```

리포트가 `.get("cells", [])` 로 읽는다. **키 이름 하나에 의존하고 있고 어디에도
적혀 있지 않다.**

**확정 필요** — `cells` 항목 스키마(영역·장르·활동 안내 문구 포함 여부).

### 2-4. `reports.report_content` 3층 구조

```
layer1   label · label_code · strengths · encouragement · recommended_preview
layer2   fluency{level,value,unit,valid} · comprehension{level,overall_accuracy,areas}
         · metacognition · weakness_training
layer3   (현재 미사용)
```

**확정 필요** — 층별 키. **부모·교사 리포트(STR-84)가 이 구조 위에 올라간다.**
지금 layer3 가 비어 있는데 계약상 무엇이 들어가는지 우리는 모른다.

### 2-5. `prescription_results.environment_adjustment`

```json
{ "success_emphasis": true, "syllable_limit": 200 }
```

문준석 STR-92 명세대로 구현했으나, **`syllable_limit` 이 어디서 소비되는지
연결돼 있지 않다.** 지금은 저장만 된다.

**확정 필요** — 소비처. 추천 지문 분량 제한에 실제로 걸 것인지.

### 2-6. `student_profiles.life_reading_graph` (A-4)

```json
[null, 2, 3, 4, null, null, null]      // 7행 고정, 미응답·비활성은 null
```

STR-120 확정대로 구현했다. 다만 **"해당 없음"(학생이 직접 고른 것)과
"비활성"(B-1 이후 학년이라 묻지 않은 것)을 둘 다 `null` 로 저장**하고 있다.
STR-124 판별식이 둘 다 제외하므로 현재 결과는 같으나, **구별이 필요해지면
지금 데이터로는 복원할 수 없다.**

**확정 필요** — 두 상태를 구별해 저장할지. 8/28 에 확인 요청했고 회신 전이다.

## 5. 형식 정형화로도 안 잡히는 것 — 함께 정해야 한다

**타입이 맞아도 뜻이 틀릴 수 있다.** 오늘 A1 결함이 그랬다.

```
산출   automaticity_score : float      (음절/10초)
소비   FLUENCY_P P33=85   : float      (음절/분)
```

**둘 다 `float` 이고 형식은 완벽히 맞았다. 6배 차이는 단위였다.**

그래서 형식 확정과 함께 두 가지를 규칙으로 두자고 제안한다.

1. **단위를 이름에 박는다.** 문준석 계약이 이미 이렇게 쓴다 —
   `A1_correct_syllables_per_minute` · `scored_time_ms` · `A4_syllable_per_sec`.
   우리 코드는 `automaticity_score` 였다.
2. **`null` 의 뜻을 형식에 적는다.** 이 프로젝트에서 `null` 은 대부분
   "측정하지 않음"이고 `0` 과 다르다. 오늘 결함 두 건(`or 0` · A2=1.0)이
   여기서 났다.
