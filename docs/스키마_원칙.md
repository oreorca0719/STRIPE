확정 **2026-09-25** (PM 승인) · 스키마 명세는 `docs/스키마_명세.md` (자동 생성)

## 0. 무엇을 하려는가

모듈이 주고받는 데이터마다 **그 데이터의 성격에 맞는 스키마**를 설계하고, 그
인터페이스의 양쪽이 스키마를 지키게 한다. 스키마를 하나로 통일하는 것이 아니다.
고정 격자, 참조 목록, 표시용 문서, 이벤트 기록은 각자 알맞은 스키마가 다르다.

**왜** — 결함이 반복해서 모듈 경계에서 났고, 모두 **에러 없이 틀린 결과**만 냈다.
파이썬은 스키마가 달라도 멈추지 않는다. dict 는 키가 틀려도 조용히 빈 값이 된다.

| 결함 | 스키마는 맞았나 | 무엇이 틀렸나 |
|---|---|---|
| A1 6배 차이 | 양쪽 다 숫자 | 단위 (음절/10초 ↔ 음절/분) |
| 태그 매칭 0/48 | 양쪽 다 문자열 목록 | 어휘 (자유 문자열) |
| 메타인지 전원 과소평가 | 숫자 | 없는 값을 0 으로 채움 |

### 용어

이 문서와 코드는 통상적인 개발 용어를 쓴다 (2026-09-26 정리).

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **스키마** | 모듈·화면 사이를 오가는 데이터의 구조 정의 (Java 쪽에서는 DTO 라고도 한다) | `backend/app/schemas/` 의 클래스. 부모는 `Schema`, DB 행에서 만드는 응답은 `RowSchema` |
| **DB 스키마** | 데이터베이스 안의 테이블·칸 구조 | `models/core.py` · 마이그레이션. 그냥 "스키마"라고 하면 위의 것이다 |
| **인터페이스** | 데이터를 주고받는 연결 하나 (내보내는 쪽 → 받는 쪽) | 명세의 절 하나 |
| **생산자 · 소비자** | 데이터를 내보내는 쪽 · 받는 쪽 | 명세 각 절 머리말 |
| **스키마 우선 개발** (schema-first) | 스키마를 먼저 정하고 코드가 맞추게 하는 방식 | 이번 규격화 전체 |
| **경계 검증** (validate at the boundary) | 데이터가 모듈에 들어오는 순간 스키마로 검사 | 모르는 키 거부·타입 변환 금지·JSONB 저장/읽기 검사 |
| **단일 진실 공급원** (SSOT) | 같은 사실을 정하는 곳이 하나뿐인 상태 | 원칙 5 |
| **허용 목록** (allowlist) | 받을 수 있는 값을 미리 정한 목록 | 주제 태그 15종 (설문 C-1 선지) |
| **코드 생성** (codegen) | 서버 스키마에서 화면 타입을 자동으로 만든다 | `frontend/src/api-types.ts` |
| **가드 테스트** | 규칙이 깨지면 실패하도록 건 테스트 | `tests/test_schema_*.py` 등 |

## 1. 공통 원칙 5가지

스키마는 인터페이스마다 다르지만, 이 원칙은 모든 인터페이스에 건다. 새 원칙은 근거와 함께
제안하고 PM 승인 후 추가한다.

| # | 원칙 | 막으려는 것 | 검사 |
|---|---|---|---|
| 1 | **단위를 이름에 넣는다** | 타입은 맞는데 단위가 다른 것 | 자동 |
| 2 | **null 은 "측정 안 함"이고 0 과 다르다** | 없는 값이 0 이 되어 결과가 뒤집히는 것 | 자동 (기본값) + 검토 |
| 3 | **정해진 값은 enum 으로 받는다** | 자유 문자열이 두 곳에서 따로 흘러가는 것 | 자동 |
| 4 | **원본과 계산값을 섞지 않는다** | 계산값만 남아 원본을 잃는 것, 둘이 어긋나는 것 | 검토 |
| 5 | **같은 사실은 한 곳에서만 정한다** | 두 곳에 적힌 값이 서로 달라지는 것 | 검토 |

### 원칙별 세부

**1. 단위를 이름에 넣는다**
- 이름 조각에 단위가 있어야 한다: `_count` `_ms` `_sec` `_ratio` `accuracy` `_pct` `_id` `syllable` `score` 등.
- 비율은 0~1 이며 `accuracy`·`_ratio` 로 쓴다. 퍼센트(0~100)는 `_pct` 로 끝낸다.
- 단위가 경우마다 달라지는 값은 **값 칸 + 단위 enum 칸을 짝으로** 둔다(예: `fluency_value` + `fluency_value_unit`). 스키마가 짝을 검사한다.
- 단위가 없어도 되는 칸은 `Unitless("사유")` 를 단다.

**2. null 은 0 이 아니다**
- 없음·측정 안 함은 `null`. 숫자 칸의 기본값을 0 으로 두지 않는다.
- "없음"이 **빈 집합**이면 null 이 아니라 빈 목록이다(예: 면책 코드 없음 = `[]`).
- 계산 결과가 정의되지 않으면 null 을 돌려준다(예: 문항 0개 칸의 정답률).

**3. 정해진 값은 enum**
- 문자열 칸은 enum 이어야 한다. 사람이 읽는 문장일 때만 `Text("사유")` 로 허용한다.
- enum 에 없는 값은 스키마와 DB 양쪽에서 거부된다.

**4. 원본과 계산값을 섞지 않는다**
- 원본(정답 수·문항 수)을 남기고, 계산값(정답률)은 원본에서 계산한다.
- **예외 — 표시용 문서**: 리포트는 학생이 본 그대로 남아야 하는 사본이라 계산값과 문구를 담는다. 원본은 판정·처방에 있다.

**5. 같은 사실은 한 곳에서**
- 다른 데이터를 가리킬 때는 복사하지 말고 id 로 참조한다(예: 추천 지문 → `text_ids`).
- 다른 칸에서 만들 수 있는 값은 저장하지 않고 계산한다(예: `matrix_position`, 보호자 안내 문구).
- **예외 — 명세가 정한 DB 조회용 칸**(`total_correct` 등)은 두되, 값은 반드시 한 곳(약점 프로필)에서 계산해 넣는다.

## 2. 강제 장치

| 자리 | 장치 | 어기면 |
|---|---|---|
| 스키마 정의 | `app/schemas/` — 모르는 키 거부, 타입 자동 변환 금지, 만든 뒤 수정 금지 | 만드는 순간 오류 |
| 모듈 → 모듈 | 스키마 객체로만 주고받는다 | 스키마 객체를 못 만든다 |
| DB JSONB | `SchemaJSONB(스키마)` 칸 타입 | 저장·읽기 모두 오류 |
| API 응답 | `response_model` 에 스키마 | 500 (틀린 값을 내보내지 않음) |
| 원칙 1·2·3 | `tests/test_schema_principles.py` 가 모든 스키마를 훑는다 | 테스트 실패 |
| 새 dict 함수 | 같은 테스트의 가드 | 테스트 실패 |
| 명세 문서 | `tests/test_schema_spec.py` | 코드와 다르면 실패 |
| 응답 스키마 없는 API | `tests/test_api_schemas.py` | 테스트 실패 |
| 화면 타입 | `frontend/src/api-types.ts` 자동 생성 (`python -m app.schemas.typescript`) · `tests/test_api_types.py` | 서버와 다르면·타입 없이 부르면 실패 |
| 화면 코드 | `vue-tsc` | 서버가 칸을 바꾸면 화면 빌드 실패 |

스키마를 어긴 것을 **테스트가 실제로 잡는지** 매번 확인한다. 통과하는 입력만
시험하면 검사가 꺼져 있어도 테스트가 통과한다(`tests/test_schemas.py`).

## 3. 스키마를 만들 때 순서

1. 이 데이터의 **성격**을 정한다 — 고정 격자인가, 참조 목록인가, 집합인가, 표시용 문서인가, 이벤트 기록인가.
2. 성격에 맞게 칸을 설계하고 **생산자·소비자·저장 위치**를 파일 머리에 적는다.
3. 불변식(칸 수, 순서, 짝, 범위)을 스키마 안에 검사로 넣는다.
4. 틀린 입력을 거부하는 테스트를 쓴다.
5. `python -m app.schemas.spec` 로 명세를 다시 만든다.
6. 흐름 레지스트리(`app/dev/flow_registry.py`) 연결선에 `contract=` 를 적는다.
