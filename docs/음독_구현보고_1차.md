## 0. 먼저 — 보류 요청분을 진행한 것에 대해

STR-16 에서 음독 방식 확정을 미루시며 **"인터페이스만 열어 두고 구현은 보류"**
를 요청하셨습니다. 그럼에도 아래 작업을 진행했고, 사후 보고드립니다.

진행한 이유는 두 가지입니다.

**첫째, 보류 사유의 전제가 달라졌습니다.** 보류 근거로 *"벤치마크 비용과
일정이 드는데 그 결과를 쓸 단계가 뒤에 있다"* 를 드셨습니다. 이번 작업은
공개 데이터와 로컬 GPU 만 썼고 **API 키도 예산도 쓰지 않았습니다.**

**둘째, 보류와 무관한 결함이 세 건 있었습니다.** 아래 §1 의 세 건은 방식
결정과 관계없이 잘못 동작하고 있던 것들이고, 그중 하나는 배포본에서 인증
없이 열려 있었습니다.

다만 STR-38(벤치마크)이 보류 목록에 있었던 것은 사실이며, 사전에 알리지
않은 것은 제 판단 착오입니다.

## 1. 고친 결함 3건

### 1-1. 분석기가 사실상 아무것도 재지 않았습니다

`analyzer.py` 가 **음절 개수만 비교**했습니다. 그래서 같은 길이의 아무 말이나
하면 만점이 나왔습니다.

| 학생이 읽은 것 | 이전 | 이후 |
|---|---:|---:|
| 완벽하게 읽음 | 1.000 | 1.000 |
| 한 단어 대치 (제비→참새) | **1.000** | 0.889 |
| **전부 다른 말** (같은 길이) | **1.000** | 0.000 |
| 절반만 읽고 중단 | 0.389 | 게이트 `fail` |

정렬(alignment) 기반으로 재작성했습니다. 정답 위치 편향(0.698)·선지 길이
편향(0.742)과 같은 계열입니다 — **과제를 수행하지 않고도 만점이 나오는
측정**이었습니다.

### 1-2. `/api/audio/*` 가 토큰 없이 열려 있었습니다

배포본에서 확인했습니다. `CLOVA_API_KEY` 가 비어 Mock 으로 떨어지는 동안은
실피해가 없으나, **키를 넣는 순간 외부에서 10MB 오디오를 던져 과금시킬 수
있는 경로**가 됩니다. 라우터 전체에 인증을 걸었습니다.

### 1-3. 정확도의 분모를 클라이언트가 보내고 있었습니다

`total_syllables` 를 요청 본문으로 받아 `1 − 오류/총음절` 을 계산했습니다.
분모를 키우면 정확도가 올라갑니다. `round_id` 로 지문을 찾아 **서버가 세도록**
바꿨습니다.

## 2. 기획 판단에 영향이 있는 발견

### 2-1. 도메인 공식은 오류 '유형' 분해를 요구하지 않습니다

문서 §2-1 의 두 공식을 그대로 보면:

```
자동성 = (정확 음절 수 ÷ 소요시간) × 10
정확성 = (생략 + 대치 + 첨가 + 반복 + 수정 총 오류 수) ÷ 총 음절 수
```

**둘 다 총 오류 수 하나만 씁니다.** 유형별 분해는 어느 공식에도 들어가지
않습니다.

STR-83 제목의 *"오류 5종 분류"* 는 제가 쓴 것인데, 문서의 유형 나열은
**산출물 요구가 아니라 '무엇을 오류로 셀 것인가'의 정의**였습니다.

**이것이 중요한 이유**: A안(완전 자동)에서 가장 어려운 부분이 유형 분류였고,
특히 반복·자기교정은 상용 STT 가 전사에서 지워 구조적으로 측정이 불가능합니다.
그게 지표에 불필요하다면 **A안의 성립 조건이 크게 느슨해집니다.**

> **확인 요청**: 유형별 분해가 처방 정교화 등 다른 용도로 필요한지 알려주십시오.
> 필요 없다면 총 오류 수만 산출하는 것으로 범위를 줄이겠습니다.

### 2-2. 소요시간을 버튼으로 재면 1.77배 느리게 나옵니다

AI Hub 아동 음성 150건 실측입니다.

```
파일 길이의 41.9% 가 무음
음절/초   파일길이 기준 3.19  →  실제 발화 구간 기준 5.64
```

지금 구현은 학생이 '시작'·'끝' 누른 간격을 씁니다. **뜸들인 시간과 늦게 누른
시간이 읽기 속도에 섞이고, 그 편차는 아이마다 다릅니다.** 버튼 조작이 서툰
아이가 느리게 읽는 것으로 기록됩니다.

발화 구간 검출(VAD)을 붙여 실제 발화 구간만 재도록 했습니다. 도메인 §2-1 의
표준 절차 *"제목 읽기 시작 순간부터 마지막 음절까지"* 를 자동화한 것입니다.

silero-vad(2MB ONNX)를 로컬 CPU 로 돌립니다. **음성이 서버 밖으로 나가지
않아 국외이전이 발생하지 않습니다.** 런타임이 없는 환경에서는 비활성으로
떨어지고 화면 측정 시간을 씁니다.

### 2-3. 학년별 읽기 속도 분포 (참고값)

AI Hub 정형 낭독 21.5만 발화 / 화자 716명.

| 학년 | P33 | 중앙 | P67 |
|---|---:|---:|---:|
| 초4 | 3.27 | 3.54 | 3.82 |
| 초5 | 3.45 | 3.76 | 4.09 |
| 초6 | 3.75 | 4.01 | 4.30 |

*(음절/초. 파일 길이 기준이라 §2-2 의 무음이 포함된 **보수적 값**입니다)*

**한계 셋을 함께 밝힙니다.**
- 발화가 **문장 단위**(중앙 22음절)입니다. 우리 지문은 문단(150~450음절)이라
  10~20배 차이가 납니다. 문단을 이어 읽을 때의 호흡·피로는 이 값에 없습니다.
- **중1(Y7)이 데이터셋에 없습니다.** G7 구간은 외삽해야 합니다.
- 녹음 기기가 모바일 69% / PC 5% 입니다. 학교 컴퓨터실과 조건이 반대입니다.

그대로 임계값으로 쓸 수는 없고, **파일럿 확정 시 참고 범위**로만 유효합니다.

### 2-4. AI Hub 데이터로는 음독 자동화를 검증할 수 없습니다

정답으로 쓰려던 필드 세 개가 **모두 정답이 아니었습니다.**

| 필드 | 기대 | 실제 |
|---|---|---|
| `ErrorTagged` | 미스큐 정답 | **전건 `N/A`** (215,199건) |
| `LabelText` | 실제 발화 전사 | **대본**. 같은 문장을 최대 25명이 읽었는데 문자열 완전 일치 |
| `SpeechStart/End` | 발화 구간 정답 | **파일 경계 관례**. `파일길이 − 0.1초` 가 97% |

따라서 **공개 데이터로 "AI 채점이 사람 채점과 얼마나 맞나"를 재는 경로가
없습니다.** 이 사실이 아래 §4 제안의 배경입니다.

## 3. 제 판단 오류 정정 3건

기록을 위해 남깁니다.

1. **"음독 결과가 판정에 도달하지 못한다"를 결함으로 보고했으나, 기획
   의도였습니다.** 유창성 판정을 묵독만으로 완결한다는 STR-16 확정을 확인
   하지 못한 채 코드만 보고 판단했습니다. 판정 경로는 그대로 두었고, 음독이
   묵독 판정을 건드리지 않는다는 것을 테스트로 고정했습니다.

2. **"발화 구간 정답이 21만 건 있다"고 판단했으나 파일 관례였습니다.**
   라벨 하나만 보고 내린 결론이었습니다. 전수로 확인해 정정했습니다.
   이 때문에 VAD 검증에서 나온 "구간 오차 34.6%"는 VAD 오차가 아니라 파일
   앞뒤 무음의 양이었습니다.

3. **`oral_reading_results` 테이블이 우리 코드에 없습니다.** STR-126 에서
   *"20개 테이블 변경 없음 확정(실측)"* 에 이 테이블이 포함돼 있는데, 실제로는
   `fluency_results` 한 테이블에 `type` 컬럼으로 음독·묵독을 통합해 두었습니다.
   같은 목록의 `silent_reading_results` · `device_checks` ·
   `user_text_interactions` · `retest_reminders` · `followup_responses` ·
   `teacher_responses` · `consents` 도 우리 코드에 없습니다(동의는
   `consent_records` 로 구현). **지금 바꿀 이유는 없다고 보나, 명세 대조 시
   참고하십시오.**

## 4. 제안 — 강제정렬(forced alignment) 방식

### 4-1. 문제를 다시 정의합니다

```
STT       음성 → "무슨 말인지 알아맞히기" → 텍스트
          ↑ 언어모델이 그럴듯한 문장으로 되돌린다 = 오류를 지운다

강제정렬   음성 + 대본 → "이 음성이 이 대본과 맞는가" → 음절별 점수
          ↑ 맞힐 필요가 없다. 답안지를 들고 채점만 한다
```

**우리는 아이가 읽어야 할 대본을 알고 있습니다.** 무슨 말을 했는지 알아맞힐
이유가 없고, "이 음절을 제대로 읽었는가"만 보면 됩니다.

### 4-2. 이 방식이 해결하는 것

| | STT 경로 | 강제정렬 |
|---|:-:|:-:|
| 대치 | △ LM 이 되돌림 | ✅ |
| 생략 | ✅ | ✅ |
| 첨가 | ✅ | ✅ |
| **반복** | ❌ 전사에서 지워짐 | ✅ 같은 구간이 두 번 정렬됨 |
| 어디서 틀렸는지 | ❌ | ✅ 음절 단위 |
| 국외이전 | 발생(상용 API) | **없음**(로컬) |
| 비용 | 사용량 과금 | **0** |

한글은 음절 문자라 정렬 단위가 자연스럽고, **도메인 공식의 분모가 음절인
것과도 맞아떨어집니다.**

이 방식은 발음평가(CAPT) 분야의 표준이며, Azure 발음평가도 같은 계열입니다
(사람 채점과 피어슨 상관 >0.5 를 자체 주장).

### 4-3. 필요한 것

한국어 음향모델(오픈 웨이트) · G2P · 정렬 구현. **전부 로컬에서 돌고 음성이
기기를 떠나지 않습니다.** 학습(파인튜닝)은 하지 않습니다 — 기성 모델로
정렬만 합니다.

### 4-4. 검증은 우리가 직접 만듭니다

AI Hub 에 정답이 없다는 것이 확인됐으므로, **우리 지문으로 정답이 확실한
검증 세트를 만듭니다.** 일부러 오류를 넣어 읽은 녹음을 만드는 방식입니다.

```
정상 낭독 / 한 낱말 대치 / 한 줄 건너뛰기 / 한 어절 두 번 읽기 / 중간 포기
```

아동 음성은 아니지만 **파이프라인이 그 오류를 잡는지는 확인됩니다.**
아동 음성에서의 정확도는 파일럿 표본 검수로 이어서 확인합니다.

### 4-5. 사람의 역할

완전 자동을 목표로 하되, **처음부터 자동으로 두지 않습니다.**

```
1단계  AI 채점 → 감독자 확인·수정        정답이 쌓임
2단계  오차가 안정되면 표본 검수로 축소   10% 등
3단계  완전 자동
```

두 가지 안전장치를 처음부터 넣습니다.

- **블라인드 표본 10%** — AI 결과를 보여주지 않고 감독자가 백지 채점.
  나머지 90% 로 잰 정확도는 자동화 편향으로 부풀려집니다. 이 10% 가 편향
  없는 유일한 자입니다.
- **승인률 추적** — 감독자가 AI 결과를 그대로 승인한 비율. 100% 에 가까우면
  확인이 형식이 됐다는 신호입니다.

## 5. 승인·결정 요청

| # | 항목 | 없으면 |
|:-:|---|---|
| 1 | **강제정렬 방향으로 진행해도 되는지** | 이 보고의 §4 전체가 대기 |
| 2 | **오류 유형별 분해가 필요한지** (§2-1) | 불필요하면 범위가 크게 줄어듦 |
| 3 | **음독 대상이 초4 확정인지** + `diagnosis_mode` 값 체계 | 화면 학년 분기를 만들 수 없음 |
| 4 | **파일럿 현장에 감독자가 있는지** (STR-79) | 없으면 §4-5 의 1단계가 성립하지 않음 |
| 5 | **음성 파일 보관 여부** | 현재 미보관 설계. 사후 채점을 하려면 보관 필요 → 방침·동의서 갱신(STR-86) |

### 함께 여쭐 것 — 사람 없이 되는 대안

감독자 확보가 어렵다면 **음독 속도 ÷ 묵독 속도**를 보조 지표로 쓰는 방법이
있습니다. 둘 다 자동 측정되고 사람이 필요 없습니다.

> 묵독은 눈으로 건너뛸 수 있지만 **음독은 모든 글자를 소리로 바꿔야 합니다.**
> 해독이 안 되는 아이는 음독이 유독 느려집니다.

음독을 붙이는 목적이 "해독이 되는가"를 보는 것이라면, 오류를 세지 않고도 그
질문에 부분적으로 답할 수 있습니다. 초4 는 어차피 둘 다 하므로 **추가 부담이
0 입니다.** 다만 도메인 문서에 없는 지표이므로 기획 판단이 필요합니다.
